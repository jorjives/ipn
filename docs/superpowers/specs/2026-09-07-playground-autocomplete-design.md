# Playground autocomplete: grammar-derived completions in the browser editor

Date: 2026-09-07. Jorj asked how much effort completion in the playground editor would be, for
an underwriter or engineer learning what they may write: dropdowns of the grammar's options and
of the names they have declared, ghost text later. Rather than a hand-written completion table
that would rot, the completions are derived from the language reference itself:
`docs/reference/grammar.md` is compiled at build time into an automaton table, committed like
the generated example pages, and walked in the browser.

## Goal

In the playground, as the author types, a dropdown offers what may legally come next on the
line: keywords of the enclosing block, continuation phrases of the line so far, and, where the
grammar wants a name, the inputs, covers, tables, items, fields and choice values the file
declares. The offer is exact with respect to the grammar page: anything offered is grammatical
and anything grammatical is offered. The grammar page therefore becomes a tested artefact:
every example and template must parse under it.

Out of scope for this spec: ghost text (inline grey suggestion accepted with Tab), which is a
follow-on once the dropdown is in; and semantic restrictions stated in the reference's prose
(which steps may appear inside `for each`, that `asks` cannot be dated). The completer may
over-offer on those; `check` still reports the error.

## Decisions

- **Buy-vs-build: CodeMirror 6, loaded as ES modules from jsdelivr.** The playground is a
  `<textarea>`; dropdowns need an editor with decorations, and hand-rolling them on a textarea
  (a mirror element to find the caret, overlays) is the commodity trap. CodeMirror's
  `@codemirror/autocomplete` supplies the dropdown, keyboard handling and accessibility; its
  `StreamLanguage` takes the regexes `idl.js` already uses so the editor colours as the
  reference pages do. jsdelivr's `+esm` endpoint serves it without a bundler, which the site
  (Jekyll, no build tooling) requires, and the page already loads Pyodide from jsdelivr. Monaco
  was the alternative: heavier, an AMD loader, and its extra machinery (diagnostics, workers)
  is not needed.
- **Buy-vs-build: derive, do not transcribe.** The grammar page is EBNF in fenced blocks. A
  compiler reads it and writes the table; nothing about the language is written twice. The
  cost is making the page's notation precise enough to read by machine, which also makes it
  precise for the page's stated audience, "anyone implementing another engine or tool".
- **The table is per-rule automata with call edges, not one flat automaton.** Expressions are
  recursive (brackets, function arguments) and referenced from some forty-five places. Inlining
  them with a nesting bound multiplies the table into thousands of states; one small minimised
  DFA per rule, with edges that call other rules, keeps it to a few hundred states, needs no
  nesting bound, and costs the runtime a stack.
- **Built at merge, not at runtime: the committed-artefact pattern the site already uses.**
  `scripts/site_pages.py` regenerates the example pages and `tests.test_site` fails when they
  are stale; the grammar table is regenerated by the same command and guarded by the same kind
  of test. The browser fetches a JSON file from the site's own assets and never sees the
  grammar page or Pyodide on the completion path, so completion works before the engine has
  loaded and costs nothing per keystroke worth measuring.
- **Operability: tests in Python, verification in the browser, CI on GitHub Actions.** The
  compiler and the walker are stdlib Python and tested by `unittest` against every example and
  template. The JavaScript walker is a port of the Python one (about fifty lines each; the
  duplication is the price of adding no Node tooling to a repo that has none) and is checked
  by driving the built site with Playwright. A workflow runs `python3 -m unittest` on pull
  requests and on pushes to `main`; requiring that check before merge is a repository setting
  Jorj sets.

### The grammar page as machine-readable input

Every fenced code block on `grammar.md` is grammar. The notation section already says what
`[ ]`, `{ }`, `|`, `'word'` and indentation mean; the compiler holds the page to it, and the
page gains one sentence saying it is read by the site's tooling. The contract:

- A rule is `name = body`; continuation lines begin with `|`. `--` starts a comment to the end
  of the line. Lower-case names are rules; a name with no definition is a terminal class.
- **Indentation in the grammar is indentation in the product.** A run of consecutive grammar
  lines indented deeper than the line before it describes the lines nested under that line.
  The compiler emits `INDENT` before the run and `DEDENT` after it, the same tokens the
  product tokeniser emits when a product line is indented deeper or shallower than the one
  before.
- A bracket group opens and closes on lines of the same indent, so nesting and bracketing
  cannot cross. `[ 'asks' { field_line } ]` in `claim_block` breaks this today and becomes
  `[ asks_block ]` with `asks_block = 'asks'` and its nested `{ field_line }`.
- **A line is a line.** Walking from `file`, each element of `file` and each alternative of an
  indented group is a *line position*. A line position that is a single rule reference
  (possibly wrapped in `[ ]` or `{ }`) delegates: that rule is a *line rule* and each of its
  alternatives is a line position. Every other line position ends with `NEWLINE`; when it
  contains an `INDENT`, the `NEWLINE` goes before it. So `cover_line`'s alternatives each end a
  line, `dated` does not (it is not in line position), and `'renewal'` followed by its nested
  `renewal_line`s reads `'renewal' NEWLINE INDENT { renewal_line } DEDENT`.
- Literals match a token by text, so `'"not selected"'` matches that string token. Terminal
  classes match by token kind: `string`, `date`, `number`, `integer` (a number without a
  point), and the word classes `name`, `word`, `item_name`, `field_name`, `collection_name`,
  `old_item_name`, which all match a word token and differ only in what the runtime offers
  (below). The compiler rejects any other undefined name, so the class list in the compiler is
  the contract.

Holding the page to this contract changes it in these places:
about ten `_block` rules (`cover`, `eligibility`, `rating`, `lifecycle`, `claims`, `scenario`,
`upgrading`, `table`, `enrichment`) put their nested `{ line }` inline and move it onto an
indented continuation, as `product_block` and `input_line` already do; the folded English
phrases (`claims in term`, `days in force`, `months in force`, `reported after N days`,
`within N days|months of inception`) become alternatives of `primary`, with the folding table
kept as the explanation of what they mean; `old_expression` and `old_condition` get
definitions (`= expression`, `= condition`). The corpus test surfaces anything else the page
omits, and each such fix is a documentation bug found, which is the point.

### The compiler: `scripts/grammar_table.py`

Stdlib only, imported by `scripts/site_pages.py` so one command regenerates every generated
site file, and by the tests.

1. **Read**: extract fenced blocks, tokenise the EBNF, insert `INDENT`/`DEDENT` from the
   grammar's indentation, parse each rule into a small expression tree of sequences,
   alternatives, optionals and repetitions over literals, terminal classes and rule references.
2. **Mark lines**: compute the line rules from `file` and place `NEWLINE` as above.
3. **Compile each rule** to an NFA over the alphabet of literals, terminal classes, structural
   tokens and rule references (Thompson construction), then to a DFA (subset construction),
   then minimise (Moore partition refinement). Rule references are ordinary edge labels; no
   rule is inlined, so recursion needs no bound.
4. **Write** `docs/assets/idl-grammar.json`: `{"start": "file", "rules": {name: {"states":
   [{"edges": {label: state}, "accept": bool}, ...]}}}` with state 0 the start state, edge
   labels as the literal text, the class name, `NEWLINE`/`INDENT`/`DEDENT`, or `→rule` for a
   call. Keys sorted, states numbered in construction order from a deterministic walk, so the
   file is byte-identical across machines and the staleness test is meaningful.

Errors are raised with the rule name and grammar line: a bracket group crossing indents, an
undefined name that is not a known terminal class, an unbalanced bracket, a rule defined twice.

Expected size: a few hundred states in total, tens of kilobytes. Not a concern beside Pyodide.

### The walker (Python for tests, JavaScript for the browser)

A configuration is a rule DFA state plus a stack of return states. Feeding a token:

1. **Close** the live set: for every configuration, follow every call edge (push the return
   state, enter the called rule at state 0) and, from every accepting state with a non-empty
   stack, pop and continue in the caller. Repeat until no configuration is new.
2. **Expected** is the union over the closed set of edges labelled by a literal, a terminal
   class or a structural token, each paired with the rule it belongs to. This is what the
   completer offers; the rule tells it that a `string` wanted by `postfix` is a table name and
   a `word` wanted by `cover_name` is a cover.
3. **Step**: keep the configurations that have an edge matching the token (by text for
   literals, by kind for classes) and move them along it. Configurations are deduplicated by
   (rule, state, stack).

The set of live configurations stays small because the grammar is nearly deterministic; the
ambiguity of a word matching both a keyword and `name` keeps a handful of them alive, no more.
A product is accepted when, after its last token, the closed set contains a configuration in
an accepting state of `file` with an empty stack.

The **product tokeniser** mirrors `parser.py`'s `TOKEN` regex (string, date, number, word
including `co-payment` and `/`, operators) and adds the structure: `NEWLINE` at the end of each
non-blank line, `INDENT`/`DEDENT` from indent changes, comments from `#` outside strings
dropped, blank lines dropped. Its Python and JavaScript versions must agree; the corpus test
holds the Python one to the parser, and the port is line-for-line.

### The completer: `docs/assets/js/idl-complete.js`

Given the document and the cursor:

- **Context** is the enclosing top-level block: from the nearest line at indent 0 at or before
  the cursor to the cursor. The walker starts at `product_block` when that line begins with
  `product`, else at `block`. Starting per block means an error elsewhere in the file does not
  silence completion; an error earlier in the same block does, and offering nothing is the
  honest answer there. (`ponytail:` walking the whole file would work and be as fast; per-block
  is the resilience choice.)
- The current line is fed without its `NEWLINE`. If the cursor sits on a whitespace-only line,
  the cursor column is that line's indent, so pressing two spaces under `cover Theft` offers
  the cover lines and pressing none offers the block keywords. The word under the cursor, if
  any, is the filter prefix, not a token.
- **Offers** come from the expected set: a literal is offered as itself; a terminal class maps
  to names scanned from the whole document, by kind:

  | Class | Offered |
  |---|---|
  | `name` | inputs, enrichment-provided fields, `asks` facts, collection fields, plus the built-in words `claim`, `claimed`, `position`, `territory` |
  | `word` | choice values, `yes`, `no` |
  | `collection_name` | inputs declared `collection of` |
  | `item_name`, `old_item_name` | the singular item names of those collections |
  | `field_name` | collection fields |
  | `word` or `string` wanted by rule `cover_name` | declared covers, quoted where declared quoted |
  | `string` wanted by rule `postfix` | table names, quoted |
  | `number`, `integer`, `date`, other `string` | nothing; the dropdown just does not appear |

  The name scan is a pass of regexes over the document's lines, tracking the enclosing block
  and indent: `name: type` lines under `inputs`, `provides` and `asks`; `choice of a, b`;
  `collection of item`; `cover X`; `table "X"`. It runs once per completion request; the
  document is small.
- The result is a CodeMirror completion list with `type` set per kind (keyword, variable,
  class, text) so the dropdown shows icons, sorted keywords first then names, both
  alphabetical. The dropdown opens as the user types and on Ctrl-Space; Enter or Tab accepts.

### The playground: `docs/assets/js/playground.js` and `docs/playground.md`

`playground.js` becomes an ES module. It imports CodeMirror (`codemirror`, `@codemirror/language`,
`@codemirror/autocomplete`, each pinned to an exact version through `cdn.jsdelivr.net/npm/...
/+esm`, which rewrites their shared dependencies to one URL each so `@codemirror/state` is
not loaded twice) and `./idl-complete.js`. The `<textarea>` becomes a `<div>` the editor mounts
in; loading an example dispatches a document replacement, Check reads `state.doc.toString()`.
Two-space indentation, `Tab` indents, the existing height and monospace styling move from the
textarea rule to `.cm-editor`. The grammar JSON is fetched from the site's own assets on page
load; if that fetch fails, the editor works without completion and the console says why.

Highlighting: `idl.js` keeps owning the token regexes and exposes one function, `classify(rest,
atLineStart, indent) → [cssClass, length]`, that its own line colourer and the editor's
`StreamLanguage` token function both call. The CSS classes stay `k`, `kw`, `ty`, `s`, `n`,
`c` so `custom.scss` colours both the same.

`playground.md` swaps the textarea for the mount element, loads `playground.js` as a module,
and its hint mentions the dropdown. `tests.test_site.Playground` keeps pinning the engine
file names and additionally asserts that every same-site asset `playground.js` fetches or
imports exists.

### Continuous integration: `.github/workflows/tests.yml`

Runs on `pull_request` and on `push` to `main`: check out, set up Python 3.12, `python3 -m
unittest`. The suite already runs every example's scenarios (through `site_pages.render`) and
fails on stale generated pages, so the one job covers engine, grammar, corpus and site.
Nothing else is installed; the project has no dependencies.

## Testing

`tests/test_grammar.py`, all deterministic, stdlib `unittest`:

- **The page compiles.** `grammar.md` reads without error; every referenced rule is defined or
  is a declared terminal class; every rule is reachable from `file`.
- **The corpus parses.** Every `.idl` under `examples/`, `examples/versioned/` and `templates/`
  is accepted by the walker. This is the drift guard between the grammar page and the parser:
  a construct the parser accepts and an example uses must be on the page.
- **Every next token was offered.** Walking each corpus file, at every token boundary the
  actual next token (its text for a literal, or a class matching its kind) is in the expected
  set. This is the contract the dropdown relies on, asserted directly rather than inferred.
- **The table is fresh.** `docs/assets/idl-grammar.json` equals what the compiler writes, with
  the same message the page test gives: run `python3 scripts/site_pages.py`.
- **Notation errors are reported**: a bracket group crossing indents and an undefined name
  each raise with the rule name.
- **The tokeniser agrees with the parser** on every corpus line: the same token texts as
  `parser.tokens`, before the structural tokens are added.

Browser verification (Playwright against the local build, not automated): the dropdown appears
under `cover Theft` with `limit`, `excess`, `excludes when`, `available when`, `in force`,
`waiting period`, `reinstatement at`; after `decline when` it offers the inputs; after
`security is` it offers `bronze`, `silver`, `gold`; Check still passes on every example.

## Documentation
